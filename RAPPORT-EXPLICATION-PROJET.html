Comment lire ce rapport

Ce document décrit les responsabilités et les interactions des fichiers, classes et principales fonctions du projet. Il explique les éléments de code par unité logique (classe, fonction, script ou configuration) : il ne traduit pas chaque mot-clé du langage Java ou Python, qui est expliqué par son contexte. Les chemins cités sont relatifs à la racine du dépôt.

Les secrets locaux, notamment le contenu du fichier .env, ne sont ni lus ni reproduits. Les rapports générés, caches, dépendances téléchargées et fichiers compilés sont des résultats d’exécution, pas des sources à maintenir. Le répertoire security-fixtures contient les dossiers iac et sca, mais aucun fichier de fixture n’a été inventorié.

Le projet est un laboratoire local d’apprentissage et d’intégration continue. Il ne doit pas être exposé comme une application de production sans authentification, TLS, gestion de privilèges et durcissement complémentaires.

1. Objectif et vue d’ensemble

devops-platform réunit une application de catalogue CRUD et un laboratoire qui automatise sa construction, ses tests, ses analyses de sécurité, son déploiement local et son observation. Le catalogue est le sujet applicatif; Jenkins, SonarQube, Trivy, OWASP ZAP, Nexus, Prometheus et Grafana constituent les outils de livraison et de contrôle.

Le parcours général est le suivant : le développeur prépare des fichiers avec pre-commit et Gitleaks, valide le message de commit avec Commitizen, puis Jenkins récupère les sources. Maven compile et teste l’API. SonarQube, Trivy et l’analyse IaC vérifient différents périmètres. Docker construit les images, Compose déploie l’application, des contrôles HTTP/runtime vérifient le résultat, Prometheus collecte les métriques, ZAP effectue un scan passif et le script de rapport rassemble les preuves.

La page HTML de DevSecOps n’invente pas de résultats : elle agrège les statuts enregistrés par le pipeline et les fichiers produits par les outils. « Étape passée » signifie que le critère d’exécution a été satisfait; cela ne signifie pas nécessairement « aucune alerte ». Une étape absente ou sans rapport ne constitue pas une preuve de sécurité.

2. Architecture et parcours d’une requête

Composants principaux :

• Navigateur → frontend Nginx sur localhost:8081.

• Nginx sert frontend/index.html et relaie /api/ vers le backend Spring Boot.

• Backend sur localhost:8080 → MySQL sur le réseau privé Compose.

• Jenkins (localhost:8083) orchestre les étapes et utilise les conteneurs Docker.

• SonarQube (9000) analyse le code; Nexus (8082) peut héberger l’artefact Maven.

• Prometheus (9090) collecte /actuator/prometheus; Grafana (3000) utilise Prometheus comme datasource.

Une lecture de produit suit ce trajet : le navigateur envoie GET /api/products à Nginx; le bloc location /api/ de frontend/nginx.conf transmet la requête à http://backend:8080/api/; ProductController appelle ProductService; le service délègue la requête SQL au ProductRepository; JdbcTemplate utilise la connexion configurée vers MySQL; le résultat remonte sous forme de Product sérialisé en JSON. La base et le backend communiquent par nom de service sur le réseau Docker, sans publier MySQL sur le port hôte.

Les contrôles ont des périmètres différents. JUnit vérifie le comportement du backend; SonarQube examine le code Java; Trivy examine les images et la configuration selon les commandes du pipeline; ZAP observe les réponses HTTP de l’API en fonctionnement; les scripts Python vérifient Compose, l’état des conteneurs, l’API et la supervision. Aucun de ces outils, pris seul, ne prouve l’absence de vulnérabilité.

3. Démarrer, vérifier et arrêter le projet

Prérequis documentés : Ubuntu sous WSL2, Java 17, Maven, Git, Docker Engine et Docker Compose v2. La pile complète (Jenkins, SonarQube, Nexus et supervision) est lourde; prévoir au moins 8 Go de mémoire pour le laboratoire, et davantage si tous les services fonctionnent en même temps.

Depuis PowerShell, ouvrir Ubuntu :

wsl -d Ubuntu

Puis, dans le terminal Ubuntu :

cd "/mnt/d/5NIDS/Labs Cybersecurity and Coding/DevOps_Project/devops-platform"
bash ./setup.sh --all
bash ./status.sh

Profils disponibles : bash ./setup.sh démarre l’application et MySQL; --tools ajoute Jenkins, SonarQube et Nexus; --monitoring ajoute Prometheus et Grafana; --all active les deux profils. setup.sh vérifie Docker/Compose, crée .env à partir de .env.example s’il manque, valide la configuration Compose, construit et démarre les services en attendant leur disponibilité. Les valeurs par défaut sont réservées au développement local; remplacer les mots de passe avant tout usage partagé.

Vérifications manuelles utiles :

curl --fail http://localhost:8080/api/health
docker compose ps
docker compose logs -f backend

Arrêt normal :

bash ./down.sh

down.sh arrête les profils Compose et conserve les volumes nommés. Cette conservation préserve les données de MySQL et des outils entre deux démarrages. La commande docker compose down -v supprime les volumes et les données persistantes : elle est destructive et ne doit être utilisée que si leur suppression est voulue.

Pour tester seulement le backend, depuis backend/ :

mvn -B clean verify

Cette commande compile, lance les tests, exécute les phases Maven de vérification et produit les rapports de tests/couverture ainsi que le JAR dans backend/target/.

4. Backend Java : fichiers, classes et API

backend/pom.xml — Décrit Maven : coordonnées du projet, parent Spring Boot, Java 17, versions forcées de Jackson/Tomcat, dépendances web, Actuator, Micrometer Prometheus, validation, JDBC, connecteur MySQL, H2 et tests. Le plugin Spring Boot empaquette le JAR; JaCoCo prépare l’agent de couverture et produit son rapport à verify. distributionManagement indique le dépôt Nexus de releases utilisé lors d’une publication configurée.

backend/Dockerfile — Construction en deux étapes. Maven/Temurin 17 compile le JAR; une image JRE plus petite exécute ensuite le paquet. curl sert aux healthchecks. L’utilisateur système app (UID 10001) exécute le processus au lieu de root.

backend/src/main/java/com/example/devops/Application.java — Point d’entrée Spring Boot. main transmet Application.class à SpringApplication.run; l’annotation SpringBootApplication active la configuration automatique et la découverte des composants.

ApiController.java — Expose GET /api/health et retourne un objet de statut de l’API, distinct des probes techniques /actuator/health.

Product.java — Record Java représentant un produit en sortie : id, nom, description, prix décimal et stock. Le type BigDecimal évite les imprécisions binaires d’un float pour les montants.

ProductRequest.java — Record de l’entrée JSON create/update. Les annotations de validation fixent des contraintes sur les champs; @Valid dans le contrôleur déclenche leur application avant le traitement métier.

ProductController.java — Couche HTTP REST sous /api/products. findAll liste les produits; findById lit un identifiant; create valide la requête et renvoie le produit créé avec un statut de création; update modifie un produit; delete le supprime et renvoie une réponse sans corps. Cette classe traduit HTTP vers les appels de service et ne porte pas les requêtes SQL.

ProductService.java — Couche métier entre contrôleur et repository. Elle centralise les opérations CRUD et transforme l’absence d’un produit lors d’une lecture/modification/suppression en ProductNotFoundException.

ProductRepository.java — Accès aux données avec JdbcTemplate. Il exécute les lectures et écritures SQL et utilise des paramètres préparés pour les valeurs fournies par le client; celles-ci sont donc des données, pas du code SQL. update et delete communiquent l’absence de ligne au service via un résultat explicite.

ProductNotFoundException.java — Exception métier spécialisée, créée à partir de l’identifiant absent; le handler commun la convertit en réponse HTTP cohérente.

ApiExceptionHandler.java — Advice Spring global. Il transforme l’exception « produit absent » et les erreurs de validation des paramètres en réponses HTTP/JSON structurées au lieu de laisser apparaître une erreur interne générique.

SecurityHeadersFilter.java — Filtre HTTP qui ajoute les en-têtes de sécurité configurés pour les réponses normales. Il agit transversalement sur la réponse, sans obliger chaque méthode du contrôleur à répéter ces en-têtes.

SecurityDemoController.java — Endpoints de test explicitement activés par configuration. weakHash démontre un usage faible de MD5 et une politique CORS permissive; weakHeaders présente une page de test où des en-têtes de protection navigateur sont volontairement absents/faibles. Cette surface est destinée à l’analyse locale ZAP, non à une utilisation métier. L’activation du mode démo doit rester contrôlée et la publication Docker est évitée quand ce mode est actif.

backend/src/main/resources/application.properties — Configuration runtime Spring, datasource et Actuator. Les variables d’environnement fournies par Compose configurent la connexion MySQL; les endpoints health/readiness et prometheus permettent les probes et la collecte des métriques.

backend/src/main/resources/schema.sql — DDL idempotent CREATE TABLE IF NOT EXISTS products : identifiant auto-incrémenté, nom, description, prix et stock. MySQL initialise le schéma au démarrage selon la configuration Spring.

backend/src/test/resources/application-test.properties — Remplace la base runtime par H2 en mémoire et utilise le mode de compatibilité MySQL; les tests n’écrivent donc pas dans la base persistante du laboratoire.

backend/src/test/java/com/example/devops/ProductControllerTest.java — Tests d’intégration MVC : endpoints de sécurité démo et headers; CRUD; rejet des données invalides et des identifiants inconnus; vérification qu’une entrée ressemblant à du SQL reste une donnée; présence d’un en-tête de protection; endpoint de métriques. Ils testent l’application HTTP dans un contexte isolé, et non les versions finales des images.

Contrat API utile : GET /api/products (liste), GET /api/products/{id} (lecture), POST /api/products (création JSON), PUT /api/products/{id} (mise à jour), DELETE /api/products/{id} (suppression), GET /api/health (statut applicatif), GET /actuator/health et /actuator/prometheus (santé technique et métriques).

5. Frontend et proxy HTTP

frontend/index.html — Application navigateur sans framework : structure HTML, présentation et JavaScript de l’écran catalogue. Elle appelle l’API sous /api, ce qui lui permet de rester sur la même origine que Nginx; les fonctions de chargement et d’actions CRUD convertissent les réponses JSON en éléments affichés.

frontend/nginx.conf — Écoute sur le port 8080 à l’intérieur du conteneur, sert les fichiers statiques et relaie /api/ au service backend. Les en-têtes Host et X-Real-IP sont transmis. Le port publié côté machine est 8081 et limité à l’interface loopback 127.0.0.1 dans Compose.

frontend/Dockerfile — Part d’une image Nginx non privilégiée, met à jour ses paquets, copie la page et la configuration puis exécute Nginx sous l’utilisateur nginx. L’image expose le port interne 8080.

6. Docker Compose et configuration des services

docker-compose.yml — Source de vérité de l’environnement local. Il déclare MySQL, backend, frontend et les profils optionnels devops et monitoring. Les healthchecks imposent l’ordre de démarrage; les ports frontend/backend sont liés à 127.0.0.1; les réseaux Compose relient les services; les volumes nommés conservent les données. Le profil devops ajoute PostgreSQL/SonarQube, Nexus et Jenkins; monitoring ajoute Prometheus et Grafana. Jenkins accède au socket Docker pour construire/démarrer les conteneurs et monte le projet dans /workspace en lecture seule : c’est un privilège élevé, adapté au labo de confiance seulement.

.env.example — Gabarit des paramètres locaux (ports, identifiants de développement, options des services); il sert à créer .env. Ses valeurs d’exemple ne sont pas des secrets sûrs. Le fichier .env local n’est pas décrit ni inclus dans ce rapport.

.gitignore — Exclut le fichier .env et les sorties Maven target des commits.

.dockerignore — Réduit le contexte de construction en excluant notamment .git, .env, target et README.

.pre-commit-config.yaml — Déclare les hooks de pré-commit, notamment contrôles de format/fichiers, détection Gitleaks et validation du message Conventional Commits avec Commitizen selon le hook-stage concerné.

pyproject.toml — Configure Commitizen avec l’adaptateur Conventional Commits; le commit attend une structure comprenant type, portée facultative et description.

7. Jenkins : déroulement réel du pipeline

Jenkinsfile — Pipeline déclaratif exécutable. Les paramètres définissent le mode source locale ou SCM, le message à valider, le mode démo de sécurité, Sonar, les publications Nexus/Docker et les notifications. Les identifiants sont attendus dans les Credentials Jenkins, pas codés dans le dépôt.

Stages dans l’ordre :

1. Declarative: Tool Install — vérifie Java, Maven, Git, pre-commit, Trivy, Docker/Compose, curl et Python.

2. Getting Project from Git — copie le dossier /workspace en mode local, en excluant .env, .git, target et rapports; sinon checkout SCM.

3. Initialize DevSecOps report — nettoie les preuves concernées puis initialise l’état du rapport.

4. Pre-commit checks — exécute les hooks sur tous les fichiers et journalise le résultat.

5. Gitleaks secrets scan — lance le hook dédié; conserve un résumé sans diffuser la sortie brute susceptible de révéler un secret.

6. Commit message validation — valide COMMIT_MESSAGE en mode local ou le dernier message Git en mode SCM.

7. Cleaning the project — nettoie le contexte et les artefacts précédents du backend.

8. Artifact construction — construit le JAR Maven en exécutant le cycle de vérification configuré.

9. Unit Tests — exécute les tests et garde le rapport JUnit comme preuve.

10. Dependency update report — collecte/présente l’état du contrôle de mises à jour prévu par le pipeline.

11. Infrastructure as Code scan — Trivy Config examine la configuration avec les sévérités HIGH et CRITICAL.

12. Code Quality Check via SonarQube — optionnel, nécessite sonar-token; exécute l’analyse Maven et récupère les issues/hotspots.

13. Building our images — construit les images backend et frontend.

14. Resolved Compose and local safeguards — résout Compose puis vérifie privilèges, exposition réseau, paramètres et protections locales.

15. Trivy vulnerability scan — analyse les images backend/frontend sur LOW à CRITICAL, sauvegarde le JSON et calcule les compteurs; les vulnérabilités HIGH/CRITICAL corrigibles sont la politique de blocage, avec poursuite contrôlée des autres scans pour recueillir les preuves.

16. Publish to Nexus — publication Maven optionnelle, conditionnée à la configuration du serveur et de ses credentials.

17. Publish Docker images — publication optionnelle avec credentials et chemin de dépôt Docker Hub; ne pas l’activer avec le mode sécurité démo.

18. Deploy our image — démarre MySQL/backend/frontend, attend les probes et interroge health/products; vérifie aussi les routes démo si activées.

19. Infrastructure runtime checks — inspecte santé, état, privilèges et utilisateur effectif des conteneurs.

20. Post-deployment security smoke tests — contrôle les routes et protections de sécurité de l’API en fonctionnement.

21. Controlled backend recovery test — redémarre le backend et vérifie son retour à l’état readiness.

22. Continuous monitoring verification — démarre Prometheus/Grafana et vérifie cible Prometheus et endpoint de santé Grafana.

23. ZAP DAST acceptance scan — lance ZAP Baseline passif sur la route démo, ou sur les produits si mode démo désactivé; produit HTML/JSON.

24. Email verification — étape de notification conditionnée à l’adresse et à la configuration SMTP.

Les blocs post enregistrent les résultats d’une étape en succès ou échec. La section post globale produit/présente les preuves disponibles et archive les rapports, y compris lorsque le pipeline échoue. L’archivage permet d’ouvrir le détail du scanner ayant émis un constat. « MEDIUM/LOW informatif » ne doit pas être confondu avec « scan absent ».

jenkins/Dockerfile — Image personnalisée du contrôleur Jenkins et outils nécessaires aux étapes locales (Java/Maven, Git, Python, Docker client/Compose, Trivy, pré-commit et dépendances associées).

jenkins/init.groovy.d/security.groovy — Au premier démarrage, configure un realm local, l’utilisateur admin fourni par variables d’environnement et une politique qui interdit la lecture anonyme; les variables doivent venir de la configuration locale/credentials.

jenkins/init.groovy.d/zz-pipeline.groovy — Crée ou actualise le job devops-catalog depuis /workspace/Jenkinsfile; lève une erreur explicite si le fichier manque et peut planifier le premier build.

8. Contrôles, rapports et dashboard DevSecOps

devsecops_checks.py — Outil CLI de vérification :

• check normalise le statut, l’identifiant et le résumé d’un contrôle.

• inspect_compose_config examine la configuration résolue, l’exposition des ports, le mode privilégié, le réseau et la présence des protections.

• inspect_runtime vérifie conteneurs, healthchecks, utilisateur non-root du backend et durcissement attendu.

• fetch_json communique avec des endpoints HTTP JSON et signale les réponses/erreurs.

• inspect_monitoring attend les cibles Prometheus et Grafana.

• inspect_security_smoke vérifie les réponses HTTP et les headers de sécurité.

• write_report sérialise les résultats JSON; main choisit la sous-commande, collecte les données et retourne un code adapté au pipeline.

devsecops_report.py — Fabrique le rapport de sécurité :

• STATUS_LABELS, PHASES et CONTROLS définissent vocabulaire, phases et contrôles réellement présentés; CONTROL_DESCRIPTIONS et REMEDIATIONS renseignent leur explication et les pistes de correction.

• now produit l’horodatage; public_build_url construit les liens destinés à l’utilisateur.

• load_results et write_results lisent/écrivent le document JSON de résultats.

• redact_sensitive_text masque les motifs sensibles avant affichage.

• initialize crée l’état initial; record ajoute un contrôle; record_check_report convertit un rapport de vérification en preuves.

• artifact_problem vérifie la présence et la lisibilité d’une preuve.

• item_artifacts, _has_artifact et _load_json_report rattachent les artefacts et parsènt les rapports JSON.

• control_evidence associe chaque contrôle aux éléments de preuve appropriés.

• _archived_artifact_url, safe_link, artifact_link et artifact_links produisent des liens prudents vers les artefacts.

• load_vulnerabilities extrait et normalise les constats des rapports réels des outils.

• generate compose le HTML et le CSS du dashboard; main expose les sous-commandes à Jenkins.

sonarqube_report.py — Client SonarQube dédié. fetch_all parcourt toutes les pages API; download collecte issues et hotspots du projet puis les écrit en JSON; main valide les paramètres CLI. Le jeton est fourni par l’environnement Jenkins, non ajouté aux fichiers de sortie.

Rapports générés sous reports/ — Les JSON Trivy, SonarQube, checks, résultats agrégés, logs pre-commit/Maven/ZAP et fichiers HTML/CSS sont des preuves par exécution. La phase initiale de Jenkins nettoie des fichiers ciblés pour éviter de confondre une nouvelle exécution avec un ancien build. Ne pas modifier ces résultats à la main pour représenter un scan.

reports/report-views/ — Pages HTML d’affichage par outil (Commitizen, pre-commit, checks, Sonar, Trivy, ZAP) et feuille de style commune. Elles rendent navigables les preuves archivées.

zap-reports/ — Espace de sorties ZAP local si une exécution y dépose des artefacts; distinguer ces sorties des sources et comparer toujours leur build/période de production.

Les dossiers security-fixtures/iac et security-fixtures/sca existent, mais sont vides dans l’inventaire effectué; ils ne constituent donc pas un catalogue de résultats à intégrer au dashboard.

9. Tests, résultats et limites

Les tests Python sous tests/ couvrent les contrôles Compose/runtime/monitoring, la génération et l’intégrité des rapports, l’extraction SonarQube, et les cas historiques associés aux fixtures. Les tests emploient unittest, fichiers temporaires et mocks HTTP : ils vérifient la logique des scripts sans appeler les services externes à chaque cas.

tests/test_devsecops_checks.py — Vérifie les protections Compose, l’échec en cas de conteneur privilégié ou port public, le runtime non-root/santé et la vérification Prometheus/Grafana.

tests/test_devsecops_report.py — Vérifie l’état du rapport, les preuves liées aux artefacts, les findings et les liens/sorties HTML.

tests/test_sonarqube_report.py — Vérifie la récupération paginée et les réponses API contrôlées du collecteur SonarQube.

backend/src/test/.../ProductControllerTest.java couvre CRUD, validation, erreurs, SQL-like comme donnée, headers, métriques et mode de démo.

Historique de validation rapporté dans le contexte de travail antérieur : Maven clean verify a réussi avec 7 tests Java; les tests Python ont réussi avec 26 cas; un build Jenkins #79 a été indiqué SUCCESS, avec constats ZAP MEDIUM/LOW et un finding Trivy MEDIUM sans HIGH/CRITICAL dans les images de ce build. Ces chiffres décrivent une exécution historique et son périmètre, pas un nouveau scan lancé pendant la création de ce document ni une garantie sur un futur commit. Relancer le pipeline pour obtenir une preuve courante.

Limites connues à prendre en compte : aucune authentification métier de catalogue; HTTP local plutôt que TLS; accès Jenkins au socket Docker conférant un pouvoir élevé; valeurs d’exemple réservées à une machine locale; ZAP Baseline est passif; Trivy et SonarQube ont des périmètres/règles définis; données persistantes dépendantes des volumes Docker. Le mode de démonstration crée exprès des réponses faibles pour qu’un scanner les détecte; ne pas l’activer sur un système exposé ou lors d’une publication.

11. Glossaire

API — contrat HTTP/JSON utilisé par le navigateur et les autres clients.

CI/CD — intégration continue puis livraison/déploiement automatisés.

DAST — analyse d’une application en fonctionnement; ici le contrôle ZAP Baseline est passif.

Finding — alerte ou constat issu d’un scanner.

JAR — archive Java produite par Maven.

SAST — analyse statique du code source; SonarQube joue ici le rôle d’analyse de qualité/sécurité configurée.

SCA — examen des bibliothèques/composants logiciels; Trivy examine notamment les images.

Image/conteneur — modèle de lancement / processus isolé créé à partir de ce modèle.

Healthcheck/readiness — signal de santé technique et de capacité à recevoir du trafic.

STRIDE — catégories de menaces : usurpation, altération, répudiation, divulgation, déni de service et élévation de privilèges.

Conclusion

Le dépôt relie une petite application Spring Boot/MySQL à une interface Nginx et à une chaîne Jenkins qui teste, analyse, construit, déploie, observe et archive les preuves. Les fichiers sources définissent le comportement; les rapports en sont les traces d’exécution. La dashboard est utile lorsque chaque carte est liée à la sortie de l’outil correspondant et au build concerné.
